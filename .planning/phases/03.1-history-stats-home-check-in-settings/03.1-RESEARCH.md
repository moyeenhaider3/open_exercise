# Phase 03.1: History, Stats, Home, Check-in & Settings - Research

**Researched:** 2026-09-29
**Domain:** Flutter/Material 3 UI on top of the Phase 3 `GymStateCubit`/JS-bridge state layer; remaining 1:1 port of openGym's analytics, home and settings screens
**Confidence:** MEDIUM-HIGH (screen/source inventory and existing-code inventory are HIGH — read directly from `../openGym` and the current Dart tree; three findings below are new domain-math/package needs that were not anticipated by Phase 3's research and need explicit user confirmation)

## Summary

Phase 3.1 finishes the six-screen "BLoC & UI Translation" scope that Phase 3's own research
(`03-RESEARCH.md`) split off into a second sub-phase: **History, Stats (minus the Phase-4 muscle
map), Home, Check-in (display/reorder/edit/delete only), and Settings**. Phase 3 already built
almost everything this phase depends on: the single-writer `GymStateCubit`, the full `ui_kit`
(rows/buttons/switches/segmented/sliders/sheets/toasts), the `AppPalette` theme extension with
dynamic accent support **already wired end-to-end** through `ShellBloc`'s
`ShellThemeChanged`/`ShellAccentChanged` events, a hand-rolled `LineChart` `CustomPainter` (built
in Plan 03-13 for exercise history), a complete `format.dart` port (`fmtNum`, `fmtDate`, `fmtDur`,
`fmtVol`, `kAccents`, `kMonthsLong`, `weekStartOf`, `weekOrder`, `weekDayOffset`, `weekKey`), a
fully-populated `HistoryJs` facade (`streakWeeks`, `lastBW`, `effectiveRoutines`,
`nextTrainingDay`, `setsDoneActive`, `workoutVolume`, etc. — every function `Home.jsx`/`Stats.jsx`
need is already bridged), and `equipment.dart`/`favourites.dart` catalogue helpers. Most of this
phase is genuinely "wire the UI to code that already exists."

Three findings, however, are **new domain-math/dependency gaps Phase 3's research did not
anticipate** and must be resolved before/while planning:

1. **Workout backfill ("Log a past workout") is explicitly assigned to this phase but not yet
   possible.** `views/History.jsx`'s "Log a past workout" button and `views/Home.jsx`'s day-tap
   calendar entrypoints both lead to `sheets.jsx`'s `logPastWorkoutSheet`/`beginBackfill`, which
   sets `active.backfill = {...}` and reuses the *live* workout screen. At finish time,
   `doFinishWorkout` branches on `A.backfill` (skips PRs, uses `backfillEnd()`, files the
   completed workout via `completeBackfill()`/`insertChronological()` instead of pushing). The
   Flutter port's own finish shim **already throws on this branch on purpose**:
   `tool/js/shims/finish-workout-shim.js:20-22` — `if (A.backfill) { throw new Error('backfill
   finish is Phase 3.1'); }`. `../openGym/frontend/src/lib/backfill.js` (`workoutsOn`,
   `backfillStart`, `backfillEnd`, `insertChronological`, `completeBackfill`) is **not yet vendored**
   into `third_party/opengym/lib/`. This is real, planned, in-scope work, not a surprise — but it
   needs its own JS-bridge module + finish-shim change + fixtures + parity re-run, not just a UI task.
2. **Stats' `EffortCard` is separable from the deferred `MuscleBalance` card and belongs in this
   phase.** Phase 3's screen map correctly scoped the `BodyMap`-based `MuscleBalance` segmented
   view out to Phase 4, but `Stats.jsx`'s `EffortCard` (effort trend + histogram) has **no
   `BodyMap` dependency at all** — it only needs `lib/effort.js` + the existing `LineChart`. The
   currently-bridged `effort` module (`rirOf`, `toScale`, `effortColor`) is a small subset; `Stats.jsx`
   also calls `hasEffort`, `displayScale`, `scaleName`, `avgRir`, `effortSummary`, `effortWeeks`,
   `effortHistogram`, `isHardSet` — all pure, all unbridged. Skipping `EffortCard` "because Stats'
   body-map card is deferred" would under-scope UI-05.
3. **Settings' unit switch ("Convert the numbers" vs "keep the numbers, relabel") needs a new,
   currently-unbridged JS module.** `lib/units.js`'s `convertStateUnit(S, to)` walks the *entire*
   `GymState` (bodyweight, targetW, exWeights, barWeights, routines, workouts, active session,
   recomputing `vol` per session) with plate-rounded conversion math. It is not vendored and not in
   `tool/js/bridge-inventory.mjs`. JS-04 requires this to be bridged (`UnitsJs`), not hand-derived.

A fourth item is a **new package, not a domain-math gap**: Check-in must render each saved gym
card's QR code from its stored string value (`components/QrCanvas.jsx`). QR generation is outside
CLAUDE.md's mandated stack (`flutter_bloc, equatable, sqflite, dio, flutter_js,
flutter_local_notifications, flutter_passkey_service, xml, path_drawing`). `qr_flutter` (pub.dev,
depends on the pure-Dart `qr` encoder) is the standard, dependency-light choice, and QR encoding is
generic rendering, not openGym business logic (same category as `path_drawing` — JS-04 does not
apply). This still needs explicit user sign-off since it is outside the locked stack.

**Primary recommendation:** Treat this phase as three JS-bridge additions (backfill, effort
extensions, units) done first, then five screens/sheet-groups built almost entirely on top of
already-existing `ui_kit`/`format`/`HistoryJs`/`GymStateCubit`/theme-event infrastructure. Confirm
the `qr_flutter` package addition and the backfill/effort/units bridge scope with the user before
planning tasks around them (see Assumptions Log).

### Pattern 1: Backfill reuses the live workout screen, gated by a flag — not a second screen
**What:** openGym's `LogPastWorkout` sheet calls `beginBackfill(...)`, which builds an `active`
session identical in shape to a live one (`buildCombinedEntries`) plus a `backfill: {durationMin,
replaceId}` field, then navigates to the **same** `/workout` route. `ActiveWorkoutView`'s elapsed
clock (D-02a, already built) must be suppressed when `active.backfill != null` — there is no live
session to time. At finish, the flow branches (Pattern 2 below) instead of routing to a different
screen.
**When to use:** `WorkoutBloc`'s start-session event family; add a `WorkoutBackfillStarted` event
alongside the existing `WorkoutStartRequested`, both converging on the same `_beginSession`-style
internal helper with a `backfill` parameter.
**Source:** `../openGym/frontend/src/sheets.jsx:1884-1907` (`logPastWorkoutSheet`,
`beginBackfill`).

### Pattern 2: Finish-flow branches on `active.backfill`, not a separate finish path
**What:** `doFinishWorkout()` in openGym is one function with an `if (past) {...} else {...}`
split; the Dart `finish-workout-shim.js`/`FinishWorkoutJs.completeWorkout` should mirror that
exactly — one JS function, one Dart call site (`_engine.finish.completeWorkout`), with the shim
now implementing both branches instead of throwing on one of them.
**When to use:** Extending `tool/js/shims/finish-workout-shim.js` and `WorkoutBloc._onFinishConfirmed`.
**Example (JS shim change target):**
```js
// Extend tool/js/shims/finish-workout-shim.js (currently throws on the backfill branch)
import { backfillEnd, completeBackfill } from '../../../third_party/opengym/lib/backfill.js';
// ...
export function completeWorkout(st, end) {
  const A = st && st.active;
  if (!A) throw new Error('completeWorkout: no active workout in state');
  const past = !!A.backfill;
  // PRs/e1PRs: only computed for a live (non-backfill) session — a workout logged into the
  // past cannot claim records against history that came after it (source comment, sheets.jsx).
  const prs = [], e1prs = [];
  if (!past) { /* existing PR/e1PR loop, unchanged */ }
  const w = buildCompletedWorkout(A, { end: past ? backfillEnd(A) : (end ?? Date.now()), prs, snapshotFor });
  w.vol = workoutVolume(w);
  // exWeights: openGym only updates this on the live path too (doFinishWorkout's `else` branch) —
  // confirm this reading against sheets.jsx before implementing; do not update exWeights from a
  // backfilled session.
  return { workout: w, prs, e1prs, past, replaceId: A.backfill?.replaceId ?? null };
}
```
The Dart side then does: `if (result.past) { workouts = completeBackfillEquivalent(...) } else {
workouts.add(result.workout) }` — `completeBackfill`'s array-splicing (`insertChronological`) is
itself pure JS-bridged logic (`BackfillJs.completeBackfill`), not something to reimplement as a
Dart list-insert.

### Pattern 3: Settings sections are thin — most rows call `GymStateCubit.mutate` directly from a Bloc event, no new sub-Blocs needed
**What:** Nearly every Settings row in openGym is a one-line `update(s => { s.field = v })`
closure. Mirror this with a single `SettingsBloc`/`SettingsCubit` whose events are one per
field-group (not one per checkbox) — e.g. `SettingsUnitChanged`, `SettingsWeekStartChanged`,
`SettingsWorkoutViewChanged` — each calling `context.read<GymStateCubit>().mutate(...)` (or, for
theme/accent, dispatching the *existing* `ShellThemeChanged`/`ShellAccentChanged` events instead of
duplicating that logic).
**When to use:** Every toggle/segmented/select row in `SettingsScreen` except the unit-switch
"convert" path (Pattern 4) and Equipment CRUD (plain list mutation, still just `mutate`).
**Anti-pattern to avoid:** A `SettingsBloc` event per individual `Row`/`Switch` (30+ events) —
Phase 3's own UI-07 checklist precedent (`03-UI07-CHECKLIST.md`) grouped closures by *screen
region*, not by DOM node; follow the same granularity here.

### Pattern 4: Unit conversion is a locked, whole-state operation via `replaceState`, not `mutate`
**What:** `switchUnit` in `Settings.jsx` offers two choices via a menu sheet: "Convert the
numbers" (`replaceState(convertStateUnit(S, v))`) or "keep the numbers, change the label"
(`update(s => { s.unit = v })`). The convert path replaces the *entire* state object (mirrors
`GymStateCubit.replaceState`, already built in Plan 03-01 for backup import/reset), not a partial
mutate.
**When to use:** Settings' Weight unit row.
**Source:** `../openGym/frontend/src/views/Settings.jsx:37-47`, `../openGym/frontend/src/lib/units.js`.

### Anti-Patterns to Avoid
- **Reimplementing `workoutVolume`/`completedVolumeOf` math anywhere in Stats/History/Home "just
  for a badge or tooltip":** every one of History's `WorkoutRow` subtitle, Stats' tiles, Home's
  streak card, and the Heatmap's tooltip reads `w.vol`/`streakWeeks`/`setsDone` — all already
  bridged; call the facade, never re-sum sets in Dart (same JS-04 trap Phase 3's Pitfall 2 flagged
  for `setLabel`).
- **Building the Stats `MuscleBalance` segmented view "since it's right there in `Stats.jsx`":**
  still explicitly Phase 4 (`BodyMap` dependency unchanged from Phase 3's research).
- **Skipping `EffortCard` on the same "deferred to Phase 4" assumption:** it has no `BodyMap`
  dependency — see Summary #2. Confirm this distinction is visible in the plan.
- **Treating "Log a past workout" as a simple form-and-save screen:** it reuses the *entire* live
  workout screen and the finish-flow branch — see Patterns 1-2. A plan that scopes it as "just a
  date/time/duration form + a database insert" will miss the backfill JS-bridge work entirely.
- **Hand-rolling QR matrix drawing to avoid adding a new package:** flagged above as a Don't
  Hand-Roll; QR encoding is a well-defined, non-trivial spec (Reed-Solomon, mode indicators) with
  no relationship to openGym's own code — `qr_flutter` (pending approval) is correct here.

new sheet-stack concerns — everything reuses `showAppSheet`/`ReorderableListView`-adjacent
precedent), but it has **more small, easy-to-miss domain-math surfaces** (volume, streak, effort,
unit conversion, chronological insertion) scattered across read-only-looking screens. The
temptation is highest exactly where the UI looks like "just print this number."

## Common Pitfalls

### Pitfall 1: Treating "Log a past workout" as new UI work only (see Summary #1, Pattern 1-2)
**What goes wrong:** A plan scopes backfill as "add a form + save it," missing that
`third_party/opengym/lib/backfill.js` isn't vendored and the finish shim deliberately throws on
this exact phase name.
**How to avoid:** Schedule the JS-bridge work (vendor + shim extension + fixtures + parity re-run)
as its own task before the `LogPastWorkoutSheet` UI task.
**Warning signs:** A plan with a `LogPastWorkoutSheet` task but no `backfill` bridge/fixture task,
or `bash tool/run_parity.sh` not re-run for this phase.

### Pitfall 2: Conflating `EffortCard` with the deferred `MuscleBalance` card (see Summary #2)
**What goes wrong:** Both live in the same `Stats.jsx` file, both are "the analytics-heavy part of
Stats," and Phase 3's own research says "ship Stats without the muscle-map card" — easy to
over-read that as "ship Stats without either heavy card."
**How to avoid:** Confirm `EffortCard` has zero `BodyMap`/`body-paths.js`/`musclesOf` imports
(verified in this research) before excluding it.
**Warning signs:** UI-05 shipped without any effort chart, even when `S.workouts` contains RIR/RPE-
rated sets.

### Pitfall 3: Building unit conversion as a Dart loop "since it's just multiplication"
**What goes wrong:** `convertWeight`/`convertBodyWeight` have different rounding granularity (0.5
lb / 0.25 kg for loaded weight vs 0.1 for body weight — chosen so a round trip lands back exactly,
per the source comment referencing QA ticket C15), and `convertStateUnit` must recompute each
session's cached `vol` from its *converted* sets rather than converting the cached `vol` number
directly (drops would double-round otherwise).
**How to avoid:** Bridge `units.js` verbatim (new `UnitsJs` facade); do not write the multiplication
in Dart even though it looks trivial.
**Warning signs:** A Dart file computing `weight * 2.2046226218` or similar inline.

### Pitfall 4: Assuming Check-in's "edit" scope includes re-scanning the code value
**What goes wrong:** D-03 (Phase 3 CONTEXT) says Check-in ships "display/reorder/edit/delete,"
which could be read as full parity with openGym's `CardSheet` (which supports both rename and
re-scan). But re-scan requires the same camera/barcode stack as "Add card" (`CameraScan.jsx`,
`lib/scan.js`), which is Phase 8 (IMP-03) exactly like "Add card" is.
**How to avoid:** Scope "edit" to label/rename only this phase; the re-scan button should be
hidden/disabled with the same Phase 8 note as "Add card." Flag this as an explicit confirmation
point, not a silent narrowing (see Open Questions).
**Warning signs:** A plan task that reintroduces `CameraScan`/`scanCode`/`importCodeFromImage` for
"editing" a card.

### Pitfall 5: The Phase 3 finish-flow "Volume (0 kg)" observation — investigate, don't assume either way
**What was found:** Plan 03-16's device walkthrough (`03-16-SUMMARY.md`, Step 6) logged: bumped
weight/reps on a straight set → checked it → added a warm-up set → checked it → added a drop set →
added a rest-pause burst → finished early. The resulting `FinishSummary` showed **Duration 30 min,
Volume 0 kg, Sets 2 sets · 1 work, PRs —**.
**What this research ruled out:** This is **not** a missing-bridge problem. `HistoryJs.workoutVolume`
is fully bridged and IS called by `WorkoutBloc._onFinishConfirmed` via
`_engine.finish.completeWorkout` → `finish-workout-shim.js`'s `completeWorkout` → `w.vol =
workoutVolume(w)` (traced end-to-end in this session). `completedVolumeOf` (the per-set summand)
correctly requires `set.done && Number(set.w) > 0` and excludes warm-ups — matching source exactly.
**What remains unresolved (needs a device recheck, not code archaeology):** With weight/reps
bumped and the set checked, `completedVolumeOf` should have been > 0 for that one "work" set — a
0 kg result implies either (a) the checked work set's `w` field was structurally reset to 0 by a
later mutation (adding a drop/burst converts the row's `type`/shape — worth checking whether
`WorkoutDropAdded`/`WorkoutBurstAdded` in `workout_bloc.dart` call the bridged `addDrop`/`addCluster`
functions, which are designed to preserve the base row, versus constructing a fresh `SetEntry`), or
(b) the specific exercise/scenario in that walkthrough legitimately had `w == 0` (a bodyweight
exercise with no added load, in which case Volume 0 kg is **correct, matching openGym**, since
`completedVolumeOf` only counts `w * r`, not bodyweight itself, for a `reps`-mode exercise).
**How to avoid it becoming an invisible Phase 3.1 regression:** History's `WorkoutRow`, Stats'
tiles/heatmap tooltips, and Home's streak card all render `w.vol` verbatim. Any real bug here
becomes immediately visible across every screen this phase builds.
**Recommendation:** Add a Wave-0 device-verification step: log a *known-weighted* straight set only
(no drop/burst conversion), finish, and confirm `Volume` is the expected `w × r`. If it reproduces
0 there too, treat it as a `WorkoutBloc` bug to fix in this phase (before building Stats/History on
top of it); if it does not reproduce, the original observation was case (b) above (bodyweight
exercise) and needs no fix.

### `BackfillJs`/finish-shim wiring target (Dart call site)
```dart
// Source: ../openGym/frontend/src/sheets.jsx:2188-2227 doFinishWorkout (backfill branch),
// paired with the extended tool/js/shims/finish-workout-shim.js (Pattern 2).
Future<void> _onFinishConfirmed(Emitter<WorkoutState> emit) async {
  final GymState s = _gymState.state;
  if (s.active == null) return;
  final bool isBackfill = s.active!.backfill != null; // new field, mirrors A.backfill
  final int now = DateTime.now().millisecondsSinceEpoch;
  final FinishResult result = _engine.finish.completeWorkout(s, now); // shim now branches internally
  await _gymState.mutate((GymState st) {
    if (result.past) {
      // BackfillJs.completeBackfill mirrors sheets.jsx's `s.workouts = completeBackfill(...)`
      final List<Workout> filed = _engine.backfill.completeBackfill(
        st.workouts ?? const <Workout>[], st.active!, result.workout,
      );
      return st.copyWith(workouts: filed, active: null);
    }
    final List<Workout> nextWorkouts = List<Workout>.from(st.workouts ?? const <Workout>[])
      ..add(result.workout);
    return st.copyWith(workouts: nextWorkouts, exWeights: result.exWeights, active: null);
  });
  _emitSignal(WorkoutFinishedSignal(result), emit);
}
```
